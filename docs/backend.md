# Backend API

The backend is a TypeScript + Fastify API server that sits between `mcp-store`, the dashboard, and the admin CLI. It handles passkey auth, persists everything to SQLite, serves the dashboard's data, and streams per-user SSE updates. See [ARCHITECTURE.md](./ARCHITECTURE.md) for context.

---

## Overview

- **Auth:** passkey only (WebAuthn). Session cookies. Strict per-user scoping on every endpoint.
- **Persistence:** SQLite via `better-sqlite3`.
- **Realtime:** SSE stream per authenticated user — `finding:new`, `run:completed`, `target:status`.
- **Writes from agents:** agents do not call the backend directly; they go through `mcp-store`. The backend's writable endpoints are for users (via dashboard / slash commands) and admins (via CLI).

---

## Framework Decision: Fastify (locked in)

**Fastify**, not Hono.

**Rationale:**

- Local/homelab deploy target — there is no edge runtime to serve. Hono's edge strengths are wasted.
- Mature plugin ecosystem — `@fastify/cookie`, `@fastify/session`, SSE plugins, WebAuthn libs all play nicely.
- Good fit for SSE and long-lived connections.
- Works comfortably with `better-sqlite3` (synchronous, same-process DB).
- TypeScript support is first-class.

---

## Auth (passkey only)

- **Registration and login** via WebAuthn. A user registers a passkey (or multiple) on a device; login is a passkey challenge/response.
- **No email/password, no magic link, no OAuth.**
- **Session cookies** issued post-auth; short-ish lifetime with sliding refresh.
- **Invite-only signup (v0.1):** `/auth/passkey/register` requires a valid invite code. Invite codes are generated by admins via `admin:invite`.
- **Recovery:** if a user loses all their passkeys, an admin runs `admin:reset` to clear the user's credentials so the user can re-register a new passkey. **There is no email/SMS fallback by design.**

See also: [Project Showalter](https://github.com/lxrbckl-dev/Project-Showalter)'s passkey pattern, which this follows.

## API Endpoints

All endpoints require an authenticated session unless noted. All returned data is scoped to the authenticated user.

### Auth

| Method | Path | Purpose | Auth |
|---|---|---|---|
| `POST` | `/auth/passkey/register` | Register a new passkey. Requires a valid invite code in v0.1. | Anonymous + invite code |
| `POST` | `/auth/passkey/authenticate` | Perform a WebAuthn challenge, issue a session cookie. | Anonymous |
| `GET`  | `/auth/session` | Return current session info, or 401 if none. | Session |
| `POST` | `/auth/logout` | Clear the session. | Session |

### Targets (CRUD)

| Method | Path | Purpose |
|---|---|---|
| `GET`    | `/targets`        | List the user's targets (with last-run info). |
| `POST`   | `/targets`        | Create a new target. |
| `GET`    | `/targets/:id`    | Target detail. |
| `PATCH`  | `/targets/:id`    | Update cadence / label / instruction / active flag. |
| (no DELETE — targets are paused, not deleted, per the project's no-deletion rule. `PATCH active=false` is the "remove" path.) |

Target request body (create):

```
{
  url_or_handle: string,        // required
  label: string,                // required, display-only
  cadence: "hourly" | "daily" | ... | { cron: string }, // default: "hourly"
  instruction_template: string, // freeform
  active: boolean               // default: true
}
```

### Findings

| Method | Path | Purpose |
|---|---|---|
| `GET`    | `/findings`                 | List findings for the user, filterable by `genre`, `target_id`, `read`, `starred`, date range. |
| `GET`    | `/findings/:id`             | Detail for one finding. |
| `POST`   | `/findings/:id/read`        | Mark read. |
| `POST`   | `/findings/:id/unread`      | Mark unread. |
| `POST`   | `/findings/:id/star`        | Star (bookmark). |
| `POST`   | `/findings/:id/unstar`      | Unstar. |

### Genres

| Method | Path | Purpose |
|---|---|---|
| `GET`   | `/genres`           | List the user's genres with counts. |
| `PATCH` | `/genres/:id`       | Rename a genre (deferred — documented intent). |
| `POST`  | `/genres/merge`     | Merge one genre into another (deferred — documented intent). |

### Favorites and Search

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/favorites`        | Starred findings (convenience alias for `/findings?starred=true`). |
| `GET` | `/search?q=...`     | Full-text-ish search across the user's findings (title, summary, source handle, genre). |

### Status

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/status` | Queue state, last-run per target, agent activity summary. Backs `/lucidindex status`. |

### SSE

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/events` | SSE stream for the authenticated user only. See events below. |

### Webhook

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/webhooks/enqueue` | External system re-enqueues a specific target. Auth by shared secret. See [docs/triggers.md](triggers.md). |

## SSE Event Types

The `/events` SSE stream is per-user. Events are delivered only to sessions owned by the user they pertain to.

| Event | Payload (shape) | Fires when |
|---|---|---|
| `finding:new` | `{ finding_id, target_id, genre, title, summary, importance, timestamp, ... }` | An agent wrote a new finding back via `mcp-store`. |
| `run:completed` | `{ target_id, queue_item_id, status, failure_reason?, findings_count, at }` | An agent acked a queue item. Drives the "last run" indicator in the queue UI. |
| `target:status` | `{ target_id, last_run_status, last_run_at, next_due_at }` | Queue-level status change (e.g. a target just became ready, or its cadence was updated). |

## Database Schema

SQLite tables. Names and columns below are draft; finalize at implementation time. All user-scoped tables have a `user_id` column.

### `users`
- `id` (pk, uuid)
- `handle` (unique)
- `created_at`
- `status` ("active" | "disabled")

### `passkeys`
- `id` (pk)
- `user_id` (fk → users.id)
- `credential_id` (unique, base64)
- `public_key`
- `sign_count`
- `device_label`
- `created_at`

### `invites`
- `code` (pk, unique)
- `created_by_admin` (bool, always true in v0.1)
- `created_at`
- `consumed_by_user_id` (nullable, fk → users.id)
- `consumed_at` (nullable)

### `targets`
- `id` (pk, uuid)
- `user_id` (fk → users.id)
- `url_or_handle`
- `label`
- `cadence` (string — named preset or cron expression)
- `instruction_template` (text)
- `active` (bool)
- `high_water_mark` (text/json, opaque)
- `last_run_status` ("succeeded-with-findings" | "succeeded-nothing-new" | "failed" | null)
- `last_run_at` (nullable)
- `last_run_failure_reason` (nullable)
- `next_due_at` (used by the cron re-enqueuer)
- `created_at`, `updated_at`

### `queue`
- `id` (pk, uuid) — this is the `queue_item_id` passed to `mcp-store`
- `user_id` (fk → users.id)
- `target_id` (fk → targets.id)
- `enqueued_at`
- `locked_by` (nullable — agent session id)
- `lock_expires_at` (nullable)
- `status` ("ready" | "locked" | "acked")

### `findings`
- `id` (pk, uuid)
- `user_id` (fk → users.id)
- `target_id` (fk → targets.id)
- `run_log_id` (fk → run_log.id)
- `source_url`
- `title`
- `summary` (text)
- `genre_id` (fk → genres.id)
- `importance` ("low" | "medium" | "high")
- `content_timestamp` (when the underlying content appeared)
- `thumbnail_url` (nullable)
- `platform` (nullable)
- `source_handle` (nullable)
- `read` (bool, default false)
- `starred` (bool, default false)
- `created_at`

### `genres`
- `id` (pk, uuid)
- `user_id` (fk → users.id)
- `name` (unique per user)
- `order` (nullable — for explicit column ordering later; v0.1 defaults to creation order)
- `created_at`

### `favorites`
- Materialized as `findings.starred = true`. No separate table in v0.1; documented here for navigation purposes.

### `run_log`
- `id` (pk, uuid)
- `user_id`, `target_id`, `queue_item_id`
- `status` ("succeeded-with-findings" | "succeeded-nothing-new" | "failed")
- `failure_reason` (nullable)
- `findings_count` (int)
- `started_at`, `completed_at`

## Admin CLI

Out-of-band flows that intentionally do not live in the dashboard.

| Command | Purpose |
|---|---|
| `admin:invite` | Generate an invite code. Prints the code to stdout. Admin hands it to the prospective user through whatever channel they like. |
| `admin:reset <user-handle>` | Clear a user's passkeys so they can re-register. The *only* passkey recovery path — no email/SMS fallback by design. |
